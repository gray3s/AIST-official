# 1. NAMED SOFTWARE COMPONENTS AND THEIR FUNCTIONS / ROLES

Before evaluating any result, the software components involved in producing
that result must be identified by name and by function.

This distinction is important because several different components participate
in a run, but they do not make the same kinds of decisions.


## 1.1 START-R12-V0-AIGPTCHESS-V6.sh

`START-R12-V0-AIGPTCHESS-V6.sh`

Functional role:

`R12 v0 launcher / entry point`

Primary responsibilities:

- starts the R12 v0 campaign;
- establishes the top-level execution path;
- invokes the R12 v0 campaign software.

This component is primarily an entry point.

It does not itself evaluate model semantics or chess-move correctness.


## 1.2 runme-r12-v0-aigptchess-v6.sh

Software component:

`runme-r12-v0-aigptchess-v6.sh`

Functional role:

`R12 v0 campaign harness / campaign orchestrator`

Primary responsibilities:

- discovers the available GGUF models;
- constructs the model inventory used for the run;
- excludes non-playable auxiliary GGUF files;
- invokes the R12 v0 qualification gate;
- reads each model's qualification result;
- admits only models whose qualification status is `PASS`;
- invokes the per-model AIGPTChess v6 worker;
- controls the campaign and clue-level execution;
- collects and organizes run results.

This component decides whether a model proceeds into the chess campaign by
reading the result produced by the qualification gate.

Its admission rule is effectively:

`qualification status == PASS`

It does NOT independently repeat the semantic qualification analysis.

It therefore acts on the qualification decision made by another component.


## 1.3 runme-r12-v0-qualification-gate.sh

Software component:

`runme-r12-v0-qualification-gate.sh`

Functional role:

`R12 v0 qualification gate`

Primary responsibilities:

- determines whether a usable communication profile exists;
- sends the qualification prompts;
- records model replies and response times;
- performs semantic validation where applicable;
- records qualification failures;
- makes the final model-level qualification `PASS` or `FAIL` decision.

This is the software component that made the disputed R12 v0 qualification
decisions.


### Qualification semantic validator

Software implementation:

Inline Bash decision logic inside:

`runme-r12-v0-qualification-gate.sh`

Functional role:

`R12 v0 qualification semantic validator`

This is not a separate executable program.

It is a distinct decision-making functionality inside the qualification gate.

Its responsibilities are:

- inspect model responses for selected qualification prompt types;
- apply implemented Bash regular-expression acceptance rules;
- apply implemented refusal/rejection rules where present;
- set semantic success or semantic failure;
- assign reason codes such as:

`instruction_state_not_confirmed`

`instruction_ack_not_confirmed`

`state_report_not_confirmed`

This functionality, rather than the language model, makes the decision that a
reply is or is not semantically acceptable for qualification.

# 4. HOW R12 v0 QUALIFICATION ACTUALLY WORKS

Decision-making software:

`runme-r12-v0-qualification-gate.sh`

Before the five qualification prompt types, R12 tries communication profiles
in this order:

`small`

`standard`

`large`

A profile is selected when the model produces a nonempty response.

If none of the profiles produces a usable response, the qualification gate
rejects the model as:

`profile_no_response`

Once a communication profile has been selected, R12 defines five prompt types:

1. `open_response`
2. `instruction_state`
3. `instruction_ack`
4. `state_report`
5. `identity_report`

Each is nominally scheduled for 3 repeats.

Maximum complete qualification workload:

`5 prompts x 3 repeats = 15 responses per model`

However, the qualification gate uses immediate rejection.

The first:

- empty response;
- failed request; or
- semantic failure

can terminate the remaining qualification work for that model.


# 5. EXACT QUALIFICATION SEMANTIC RULES

Decision-maker:

`R12 v0 qualification semantic validator`

Software location:

`runme-r12-v0-qualification-gate.sh`

The semantic validator begins each applicable evaluation with:

`semantic_ok=1`

`open_response` and `identity_report` therefore receive no additional semantic
content test.

A nonempty response is sufficient for that portion of those prompt types.

Three prompt types receive explicit semantic validation.


## instruction_state

Implemented acceptance rule:

The response must contain, case-sensitively, at least one of:

`ready`

`prepared`

`able`

`can`

AND at least one of:

`chess`

`position`

`analy[sz]`

Implemented rejection rule:

Reject when either required positive pattern is absent.

There is no refusal check in the `instruction_state` semantic branch.


## instruction_ack

Implemented acceptance rule:

The response must NOT match the implemented refusal expression.

It must also contain, case-sensitively, at least one acknowledgement form,
including:

`acknowledge`

`acknowledged`

`received`

`understood`

`got it`

`okay`

or the implemented forms corresponding to:

`ok`

and:

`yes`

Implemented rejection rule:

Reject if:

- the refusal expression matches; OR
- no acknowledgement expression matches.


## state_report

Implemented acceptance rule:

The response must NOT match the refusal expression.

It must contain, case-sensitively, at least one of:

`ready`

`prepared`

`able`

`can`

AND at least one of:

`chess`

`position`

`analy[sz]`

`process`

Implemented rejection rule:

Reject if:

- the refusal expression matches; OR
- either required positive expression fails to match.


## Case-handling behavior

The qualification gate uses Bash:

`[[ string =~ regex ]]`

The qualification source does NOT normalize the response to lowercase before
these semantic tests.

It also does not enable case-insensitive Bash regex matching.

The semantic qualification tests are therefore case-sensitive.

This implementation property is central to several of the recorded R12 v0
qualification failures.

# 10. IMPORTANT PROPERTIES OF THE QUALIFICATION SOFTWARE

The qualification gate has several independent implementation properties.


## Case-sensitive positive matching

This produces the mechanically identifiable capitalization failures described
above.


## Case-sensitive refusal matching

The refusal expression is subject to the same case-sensitive Bash behavior.


## No refusal check in instruction_state

`instruction_ack` and `state_report` explicitly test refusal language.

`instruction_state` does not.

This creates a potential false-positive path in addition to the observed
false-negative path.


## Narrow lexical matching

Semantically related forms such as:

`readiness`

are not necessarily recognized by expressions built around:

`ready`


## Immediate rejection

The first semantic failure terminates qualification for that model.

Therefore the nominal 3-repeat structure does not protect a model from a
single semantic-classifier false negative.


## SLOW is not automatically FAIL

A nonempty response beyond the configured response threshold can be recorded:

`SLOW`

without itself causing model failure.

No SLOW qualification responses occurred in this run.

# 13. HOW THE CHESS-SIDE DECISION WORKS

Primary chess execution software:

`aigptchess-v6-r12-v0-worker.sh`

Controller interface:

`controller_exchange()`

Chess-analysis engine:

`Stockfish 16`

Model inference backend:

`llama-server`

Model being evaluated:

`GGUF model`


## Chess model system prompt

`You are the AIGPTChess v6 chess agent playing White. Follow the move request`
`exactly. Do not explain your answer.`


## Required output

The chess request requires exactly one UCI move matching:

`[a-h][1-8][a-h][1-8][qrbn]?`

and nothing else.


## Chess response decision-maker

Decision-making software:

`aigptchess-v6-r12-v0-worker.sh`

Functional role:

`chess response validator / worker`


## Exact-format acceptance criterion

The worker normalizes the model response and requires the entire reply to
match:

`^[a-h][1-8][a-h][1-8][qrbn]?$`


## Legality acceptance criterion

If the syntax is valid, the resulting UCI move must also appear in the legal
move list obtained through the controller/Stockfish side.


## Rejection categories

No usable model response can produce:

`NO_REPLY`

A nonempty response with incorrect syntax can produce:

`INVALID_REPLY_FORMAT`

A syntactically valid but illegal move can produce:

`INVALID_REPLY_LEGALITY`


## Retry behavior

The worker permits 3 attempts.

Timeout and token allowances rise between attempts.

The essential chess request remains the same.


## Final classification

After 3 invalid replies, the worker can produce:

`MODEL_COMMUNICATION_LOSS`

with termination reason:

`model_invalid_reply_after_3_attempts`

This final classification is made by:

`aigptchess-v6-r12-v0-worker.sh`

It is NOT made by:

- the model;
- Stockfish;
- the qualification gate;
- ChatGPT post-run analysis.

# 15. RETRY BEHAVIOR

The 3-attempt mechanism does not correct many deterministic formatting errors.

Examples include:

`f2`
`f2`
`f2`

and:

`c6`
`c6`
`c6`

Increasing timeout or token limits does not address that failure mechanism.

Future retry policy should distinguish:

- no response;
- delayed response;
- truncated response;
- malformed response;
- deterministic malformed response.

That would allow different recovery actions for different failure mechanisms.

# 19. NEXT R12 REVISION PRIORITIES

1. Normalize qualification semantic matching for capitalization.

2. Review lexical acceptance coverage such as `ready` versus `readiness`.

3. Apply refusal detection consistently where appropriate.

4. Reconsider immediate termination after one semantic failure.

5. Preserve distinct qualification classifications for:
   - transport failure;
   - no response;
   - empty response;
   - semantic failure;
   - slow response.

6. Preserve distinct chess classifications for:
   - no reply;
   - invalid UCI format;
   - illegal move;
   - mixed communication failure;
   - resource failure.

7. Keep software-component responsibility explicit in every analysis.

8. Preserve the exact prompt, exact model response, decision-maker,
   acceptance rule, rejection rule, and recorded result at each important
   decision point.

9. Keep model behavior, controller behavior, harness behavior, qualification
   behavior, and post-run analysis as separate evidentiary layers.
